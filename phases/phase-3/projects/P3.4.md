# P3.4 — `driftwatch` · driftwatch layer 4

> Multi-tenant driftwatch with passkeys, API keys and roles - plus a written threat model that names its own weaknesses.

**Phase 3** · ships week 20 · Cloudflare Workers + Neon · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P3.4`

## Why this one

Layer 3 gave the spine a public API anyone could call; this layer gives it real accounts,
organizations and roles, so "anyone" becomes "a member of one org, seeing one org's scans."
It depends on [`P2.2`](../../phase-2/projects/P2.2.md) strictly — there is nothing to
protect until there is an API to protect — and it lands the pattern the rehearsals taught
you: [`P3.1`](P3.1.md) for sessions, [`P3.3`](P3.3.md) for the passkey login you reuse
here, [`P3.2`](P3.2.md) for the habit of reading the spec. It sits last in the phase for
exactly that reason: `P3.1`–`P3.3` are drills, this is where the pattern goes onto the
thing you keep. The phase precedes deployment because you should never deploy something
publicly that you don't yet know how to secure — and the multi-tenancy hardening in the
capstone [`C1`](../../phase-8/projects/C1.md) starts from this layer, not from scratch.

## What you'll be able to do after

- You will have enforced authorization at the query layer rather than the route layer, and
  can explain why a route guard is the wrong place for a tenancy check.
- You will have issued and verified API keys for non-interactive callers, and can say how
  they differ from a user session in lifetime, scope and revocation.
- You will have written a threat model mapping every surface of your own service to a named
  category, and found and fixed at least two real access-control bugs in your own code.

## Build plan

| # | Milestone | Roughly | Done when |

| 1 | `orgs`, memberships, roles; migration runs clean | 2 hrs | Every scan and finding belongs to exactly one org |
| 2 | Passkey login wired in, session scoped to an org | 2 hrs | The API sees both a subject and a tenant |
| 3 | Roles enforced in the queries; API keys for CI | 3 hrs | A viewer's read succeeds and their write is refused *by the query* |
| 4 | `THREAT_MODEL.md` + fix two issues it surfaces | 3 hrs | Two commits reference two rows of your own threat table |

**Definition of done** — a deployed multi-tenant `driftwatch` where two orgs cannot see
each other's scans, a CI-usable API key, `THREAT_MODEL.md` mapping every surface to a named
category, a permission matrix in the README, and the two bugs you found written up; the
ship checklist in [`../README.md`](../README.md) green.

## Where you'll get stuck

- **Tenancy leaks through the one query you forgot** — route-level guards make every handler
  look safe while any query missing its org predicate quietly returns another tenant's rows.
  → Make the filter structurally unavoidable: one accessor layer that cannot build a query
  without a tenant, then a test asserting a cross-tenant read returns nothing. Expect this
  to be one of your two bugs.
- **API keys that are really passwords** — storing a key you can read back, or comparing it
  naively, reproduces the mistakes you just spent three weeks learning about. → Store a
  hash, compare in constant time, and give every key an owner, a scope and an expiry.
- **The threat model turns into a week of prose** — it is a document, so it has no natural
  stopping point and will absorb whatever hours remain. → Timebox it, use the category list
  named in [`../verified/`](../verified/) and quote its titles exactly rather than from
  memory, one table row per surface, stop. Week 20 is also where week 16's reduced holiday
  hours were meant to be recovered, so there is less slack than the hour count suggests. If
  a fix outgrows the timebox, the 2-hour rule's escape hatch applies: file an issue on your
  own repo and name it in the threat model as a known weakness. A model that admits a gap
  reads senior.

## The interview angle

"How do you do multi-tenancy" is a standard mid-level system-design question, and this gives
you an answer with a real schema behind it, including why the check belongs at the data
layer. Broken access control is the category interviewers probe hardest because it is the
one that bites. Resume line: *multi-tenant service with passkey login, scoped API keys and
role enforcement at the query layer, shipped with a threat model naming its own weaknesses.*
The follow-up is row-level security, or SSO — both cut; per-agent scoped credentials arrive
later with the MCP work.

## Scope discipline

**Out of scope** — no SSO or SAML, no audit-log UI, no pen-test, no compliance work. Each is
a project in its own right, and none changes whether tenancy holds.

**Stretch** — per-agent API keys with task-scoped expiring credentials, anticipating phase
6's MCP work. Only after the ship checklist is green.
