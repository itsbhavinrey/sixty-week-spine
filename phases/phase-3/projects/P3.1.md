# P3.1 — `authlab`

> Three ways to keep a user logged in, one of them deliberately broken, and a page that shows you exactly how it breaks.

**Phase 3** · ships week 16 · Cloudflare Workers + Neon · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P3.1`

## Why this one

Every service you build after this keeps someone logged in, and the answer most tutorials
hand you — a token in `localStorage` — is wrong in a way that stays invisible until someone
lands an XSS. Building all three modes side by side, the broken one included, turns "use
httpOnly cookies" from advice you repeat into a decision you can defend. It sits at week 16
because [`P1.3`](../../phase-1/projects/P1.3.md) and phase 1's cookies-vs-tokens week
already told you what the transport guarantees, so you are choosing what goes in a cookie
rather than guessing what a cookie is. The phase precedes deployment on purpose: never
deploy publicly what you cannot yet secure. Both [`P3.2`](P3.2.md) and [`P3.3`](P3.3.md)
assume this session store.

## What you'll be able to do after

- You will have written a password verifier with a memory-hard KDF, and can say which
  parameter you traded away and what it cost.
- You will have implemented both a server-side session and an access/refresh pair, and can
  say which a given system should use without hedging.
- You will have broken your own auth on camera, and can explain why `httpOnly` divides an
  XSS that reads the page from one that owns the account.

**Definition of done** — one deployed URL where a visitor switches modes, logs in three
ways and watches the third get stolen; the GIF, the decision table and your KDF parameters
with reasoning in the README; the ship checklist in [`../README.md`](../README.md) green.

## Where you'll get stuck

- **Password hashing that runs locally and refuses at the edge** — a memory-hard KDF wants
  the memory and CPU time a metered serverless runtime rations. → Read the KDF parameter
  guidance in [`../verified/`](../verified/) first, pick parameters you can defend against
  the runtime's real ceiling, put the constraint in the README, move on. Two hours of
  parameter tuning is the wrong two hours.
- **The broken mode isn't convincingly broken** — your templating escapes the payload, so
  the demo reads as a bug in your demo rather than a lesson. → Add one deliberately
  unescaped sink and say in the README that you opened the hole on purpose.
- **Cookies that work on localhost and vanish once deployed** — `Secure`, `SameSite` and
  domain scoping change once page and API stop sharing an origin. → Settle the origin
  topology before debugging. Still guessing at two hours: the 2-hour rule applies, reduce
  to one `Set-Cookie` and one `fetch`.

## The interview angle

The filter question is "when would you not use a JWT", and this is the answer: short-lived
access tokens buy stateless verification and cost revocation. The system-design rep is
where session state lives when no single server holds it. Resume line: *three
interchangeable auth modes behind one interface, with a live demo of how the popular one
fails.* The follow-up: "how do you revoke a token before it expires?" Honestly, you cut the
revocation list, and the session mode needs none.

## Scope discipline

**Out of scope** — no OAuth (that is [`P3.2`](P3.2.md); mixing them doubles the surface),
no MFA, no user-management UI, no password reset. Each is a multi-hour build with its own
edge cases, and none changes what this proves.

**Stretch** — session fixation and CSRF demos with and without `SameSite`. Only once the
ship checklist is green; week 16 is a reduced holiday week, so the stretch drops first.
