# P3.2 — `oauth-from-scratch`

> A working OAuth 2.1 authorization server and client, built from the spec rather than from a library.

**Phase 3** · ships week 18 · Cloudflare Workers + Neon · difficulty High
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P3.2`

## Why this one

Most people who say they know OAuth configured a library that hid the flow from them, and
it shows the moment someone asks what PKCE actually prevents. Writing both halves — the
authorization server and a separate client that completes the flow against it — is the only
way to own the redirect, the state parameter and the code exchange rather than trust them.
It follows [`P3.1`](P3.1.md) because you need a session and a logged-in user before there
is anything to consent on behalf of, and the phase precedes deployment for the usual
reason: never deploy publicly what you cannot yet secure. Phase 6's MCP work sits on top of
this — that auth story is this flow with a different client.

## What you'll be able to do after

- You will have implemented the authorization code flow with mandatory PKCE end to end,
  and can draw it on a whiteboard without notes.
- You will have written exact redirect-URI matching, and can explain what prefix or
  wildcard matching lets an attacker do.
- You will have built refresh rotation with reuse detection, and can say what happens to a
  client that replays an old refresh token.

## Build plan

**This project spans two weeks.** Week 17 is the build week and ships nothing; the project
ships in week 18. That is deliberate, not slack to reclaim.

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | Client registry, `.well-known` discovery | 2 hrs | A client fetches your metadata and finds your endpoints |
| 2 | `/authorize`, consent screen, code issuance | 4 hrs | A logged-in user consents and lands back with a code |
| 3 | `/token`: PKCE check, exact redirect match | 4 hrs | A tampered verifier or mismatched redirect is refused, with a reason |
| 4 | Refresh rotation + the client app | 3 hrs | The separate client app completes the flow and refreshes |

**Definition of done** — a deployed authorization server and client app, a recorded
end-to-end flow, a sequence diagram, and a README paragraph on what PKCE prevents and why
it is mandatory even for confidential clients; the ship checklist in
[`../README.md`](../README.md) green.

## Where you'll get stuck

**This is a flagged overrun.** [`plan/03-reality-check.md`](../../../plan/03-reality-check.md)
names two projects that will take roughly twice their estimate, and this is one. Going long
here is the plan working as designed, not a verdict on you — it is why the build is split
across two weeks. Apply the 2-hour rule aggressively.

- **"It just redirects back"** — the redirect/callback/state/PKCE surface has many distinct
  failure modes that all present as the same silent bounce to your callback with nothing
  useful in hand. → Log every parameter at every hop before debugging, then reduce to a
  hand-built URL and a `curl` to `/token`. Falsifiable sentence: "I expect the code
  exchange to return a token, I observe an error with no body."
- **Callback origin registered once** — the flow works locally and fails deployed because
  the URI you registered is the local one, and exact matching is doing what you built it to
  do. → Register both, and take the failure as proof it works.
- **State and verifier conflated** — you store the verifier where the state belongs, or
  reuse one across concurrent logins; the symptom is intermittent failure that reads as a
  race. → One short-lived per-attempt record holding both, keyed by state.
- **Still stuck at four hours** — step 5 applies: ship the broken piece behind a flag, open
  an issue on your own repo stating it in falsifiable form, move on. Never let one redirect
  bug eat a week.

## The interview angle

"Walk me through the authorization code flow" is a standard India PBC question, and this is
the version of the answer that includes the attacks. The system-design rep is token lifetime
and revocation across services. Resume line: *an OAuth authorization server and client
written against the spec, PKCE mandatory, refresh rotation with reuse detection.* The
follow-up is dynamic client registration or full OIDC — both cut; check the registration
story in [`../verified/`](../verified/) before claiming anything about it.

## Scope discipline

**Out of scope** — no implicit or password grants (removed from the spec; say so in the
README), no device flow, no full OIDC UserInfo, no dynamic client registration. Each is
another endpoint with its own failure modes, and this is already the phase's hard one.

**Stretch** — token exchange (RFC 8693) for a service-to-service hop. Only after the ship
checklist is green. Given the overrun flag, expect to skip it.
