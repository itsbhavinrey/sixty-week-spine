# P0.1 — `ship-kit`

> A TypeScript project template that goes from clone to live URL in ten minutes, with tests, CI and supply-chain checks already wired.

**Phase 0** · ships week 1 · Cloudflare Pages + GitHub template repo · difficulty Low
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P0.1`

## Why this one

The artifact is not the payoff. About twenty more repos in this plan start with `mkdir`, and
each otherwise costs two or three hours of re-deciding a test runner, re-writing a workflow
file and re-remembering how the deploy is wired. That tax, paid twenty times, is a phase. The
exit criterion in [`../README.md`](../README.md) — `mkdir` to a live URL with tests, CI and a
working README in under 40 minutes without looking anything up — is only reachable if those
decisions get made once. It sits in week 1 because nothing can precede it: [`P0.2`](P0.2.md) is
the first repo that consumes it, and the first honest test of whether the ritual holds.

## What you'll be able to do after

- You will have written the workflow file yourself and can say what each stage does, which
  stages fail the build closed, and which only warn.
- You will have picked a test runner, a formatter/linter, a secret scanner and a static
  analyser over their named alternatives, and can defend each in one line.
- You will have configured strict TypeScript from empty, can explain what `satisfies` buys over
  a plain annotation, and will have an ADR to point at instead of narrating a decision.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | Strict compiler config from empty, test runner with a coverage gate | 3–4 hrs | a trivial module is `satisfies`-checked; the gate fails when you delete a test |
| 2 | Format/lint plus the two supply-chain scans, each one local command | 2–3 hrs | each exits nonzero on a planted violation |
| 3 | The workflow: test → scan → build → deploy | 4–5 hrs | a push to the default branch lands a live docs URL, no dashboard clicking |
| 4 | README's six sections, CI diagram, first ADR, repo marked as a template | 3–4 hrs | someone else's clone deploys without asking you a question |

**Definition of done** — a stranger clones the template, follows the quickstart, and has their
own live URL in under ten minutes; the ship checklist in [`../README.md`](../README.md) is
green.

## Where you'll get stuck

- **Module resolution disagreements** — there is no application code here, so nearly all
  friction is plumbing: compiler, test runner and bundler resolve extensions and module formats
  differently → read the resolution docs of the tool that is actually failing, not a blog post
  about the combination.
- **Green locally, red on the runner** — the runner has no globally installed tooling, a
  case-sensitive filesystem and a clean lockfile install → make one job do nothing but run the
  command you run locally, and pin what the workflow installs.
- **The deploy credential** — the first deploy fails on auth because the token's scope is
  narrower than the deploy needs, or the target project does not exist yet → create it once by
  hand, then point CI at it. Let the 2-hour rule fire here: pushing a commit to test each fix
  is a slow loop, so run the workflow's steps locally first.
- **Scanner noise on an empty repo** — the secret scanner flags example env files and fixtures,
  so you start ignoring either the gate or everything → write the ignore file deliberately, one
  comment per rule.

This is a low-difficulty project. If it eats more than a week's hours, that is information
about the ritual rather than a failure.

## The interview angle

"Walk me through your CI pipeline" and "how do you know a dependency you pulled in is safe"
both become answers about something you built. The system-design rep is small but real: a
pipeline is a staged system with fail-closed and fail-open steps, scoped secrets, and a deploy
that has to be safe to repeat. Resume line: "authored the TypeScript template behind every repo
below — strict types, coverage gate, secret and static scanning, deploy on merge." The
follow-up is usually build provenance and signed artifacts; the honest answer is that Docker
and signing are deferred to phase 4, where there is something to containerise.

## Scope discipline

**Out of scope** — application logic (a second thing to maintain), Docker (phase 4), monorepo
tooling (you have one package). Each cut is an hour spent on the workflow instead.

**Stretch** — publish it as a `create-ship-kit` scaffolder runnable through npx. Only once the
ship checklist is green: that is a second artifact with its own packaging problems.
