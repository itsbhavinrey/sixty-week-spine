# C1 — `driftwatch` · driftwatch layer v1.0

> Know what rotted in your dependency tree while you weren't looking - with the changelog evidence for every claim.

**Phase 8** · ships week 60 · Cloudflare Workers + Neon + GitHub App · difficulty High
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `C1`

## Why this one

The capstone builds nothing new: the spine already contains a product, it is just not
assembled, not public and not explained. Layer 1's CLI
([`P0.2`](../../phase-0/projects/P0.2.md)) reads a `package.json`, layer 2's schema
([`P1.2`](../../phase-1/projects/P1.2.md)) is the memory behind "what changed since last
week", layer 3 ([`P2.2`](../../phase-2/projects/P2.2.md)) puts a contract-first API over it
with a test suite behind that ([`P2.4`](../../phase-2/projects/P2.4.md)), and layer 4
([`P3.4`](../../phase-3/projects/P3.4.md)) makes it multi-tenant and authenticated. Layers 5
and 6 ([`P4.3`](../../phase-4/projects/P4.3.md),
[`P5.2`](../../phase-5/projects/P5.2.md)) are why it survives traffic: one trace across a whole
scan, and scanning off the request path. Layer 7
([`P6.4`](../../phase-6/projects/P6.4.md)) is the part users tell other people about — a cited
answer to "what actually breaks if I upgrade" — with the MCP server
([`P6.5`](../../phase-6/projects/P6.5.md)) exposing that to agents and layer 7b
([`P6.7`](../../phase-6/projects/P6.7.md)) making retrieval cheap enough to leave running.

What this phase adds is the product face: org isolation enforced at the query layer, per-org
quotas, real onboarding; the public Drift Index — a scheduled scan over the most-depended-on
npm packages, published as an open dataset and staleness leaderboard; a GitHub App that opens
a weekly drift report with cited upgrade notes; an `ARCHITECTURE.md` with per-layer ADRs
backfilled; a published SLO and cost page. The dataset is the launch artifact: a public
dataset gets shared, a landing page does not.

The other half of the phase is not code. Applications start in week 57 and run in parallel with
the build, not after it: [`plan/03-reality-check.md`](../../../plan/03-reality-check.md) puts
the search at five to six months from first application to offer. Do not wait until you feel
ready. The last repos land while you are already interviewing.

## What you'll be able to do after

- You will have walked one request end to end through every layer you wrote yourself, and can
  name the failure mode each layer was added to handle.
- You will have enforced tenant isolation at the query layer rather than in handlers, and can
  say exactly where that isolation stops holding.
- You will have published a dataset other people cite, produced on a schedule, and can explain
  what engineering keeps it cheap enough to leave on a schedule.
- You will have an `ARCHITECTURE.md` with a diagram, an ADR per layer and a "what I'd do
  differently" section — and can talk through a decision you would now reverse.

## Where you'll get stuck

- **Multi-tenancy hardening turns into a rewrite.** Isolation at the query layer touches every
  read path you wrote, and the first attempt is a scatter of predicates in handlers → push it
  into one place all data access goes through, and let a test that hand-types a foreign org ID
  be the proof. This is where the 2-hour rule fires: falsifiable sentence, one query, stop
  rewriting the API.
- **Polishing instead of launching.** The launch post waits for the product to feel finished,
  and it never does → fix the launch week first and publish whatever is true then. The dataset
  and the limitations section are the post; an imperfect service is not a reason to hold it.
- **The portfolio pass expands without limit.** Every README you reread will look worse than
  you remember, and week 56 absorbs as much time as you give it → one hour per repo, the
  sixty-second test as the only bar, no code changes during the pass.
- **Interviewing while still building.** From week 57 the context-switching feels like it is
  ruining the build → [`plan/03-reality-check.md`](../../../plan/03-reality-check.md) is blunt
  about this: interview feedback is a stimulant no amount of studying replaces. Week 60 is a
  buffer week — protect it for the applications wave and the overruns, not for new scope.

Size the Drift Index scan against what your accounts actually allow; check
[`../verified/`](../verified/) for the ceilings before deciding how wide and how often it runs.

## The interview angle

This is the repo that answers "walk me through a system you built" in an India product-company
loop, and it is the remote-visibility play. The roadmap's argument holds: a pile of
disconnected tutorial repos reads as tutorials, while one system that visibly grew from a CLI
into a multi-tenant service with retrieval, published evals, an MCP server and a load-test
graph is a different conversation. The system-design rep buried in it is multi-tenancy —
isolation, per-tenant quotas, noisy-neighbour behaviour on shared infrastructure. Resume line:
*built and launched a multi-tenant dependency-currency service — contract-first API, passkey
auth, traced and SLO'd, queue-backed scanning, cited retrieval with published evals and an MCP
server — plus an open dataset of npm ecosystem staleness.* The follow-up a good interviewer
asks next is where isolation stops: the scan queue is shared, so one large org can delay
others, and quotas bound that rather than fix it. The second is what you cut — other
ecosystems, billing, SSO.

## Scope discipline

**Out of scope** — other package ecosystems; a billing system; a mobile app; SSO/SAML; anything
needing a paid tier. Each is a phase of work on its own, and every hour spent on one is an hour
not spent on the launch and the applications, which are what this phase exists for. Pick npm
and be excellent at it.

**Stretch** — stars from strangers, or one company using it. Either turns "portfolio project"
into "product I shipped" in every interview. Only after the ship checklist is green: a stretch
goal that eats the launch is a failure, not an upgrade.
