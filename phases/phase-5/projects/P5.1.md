# P5.1 — `cache-ladder`

> The same endpoint at four cache layers, with the hit rates and latencies that tell you which one was worth it.

**Phase 5** · ships week 27 · Cloudflare Workers + Upstash · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P5.1`

## Why this one

Everyone can name a cache. Far fewer can say which layer a cache belongs in, or what it
costs when the answer is wrong. So you build one deliberately expensive endpoint and serve
it four ways — no cache, in-Worker memory, Upstash as a cache-aside store, and the edge
Cache API — and measure all four. The ladder is the deliverable, not any one rung: a single
cache is an afternoon's work, the comparison is what you can defend. It sits at week 27
because you can finally see what you are caching — the traces from
[`P4.3`](../../phase-4/projects/P4.3.md) turn "this endpoint feels slow" into a measured
cost. [`P5.4`](P5.4.md) reuses the same before-and-after discipline, and the argument
returns for model calls in [`P6.7`](../../phase-6/projects/P6.7.md).

## What you'll be able to do after

- You will have written a cache-aside path yourself and can explain who writes the entry on
  a miss, and why the read path must survive the store being unreachable.
- You will have caused a stampede on purpose and fixed it with single-flight, and can
  explain why a cold key under concurrency is worse than no cache at all.
- You will have four measured rows and can argue which rung to keep, which to delete, and
  where invalidation happens in each — including the case where the answer is "none of
  them".

## Where you'll get stuck

- **The numbers refuse to sit still** — memory beats Upstash on one run and loses on the
  next, because cold starts, network variance and a warm upstream all move more than the
  cache does. → fix the request count, discard the warm-up, report a distribution. The
  2-hour rule fires here: if you are tuning the harness rather than the cache, write the
  falsifiable sentence and stop.
- **Two rungs disagree about what is true** — you invalidate the shared store and the edge
  keeps serving the old body. → derive every key through one function, decide the
  invalidation order explicitly, and write that order in the README. This is the interview
  question in disguise.
- **The week quietly produces nothing.**
  [`plan/03-reality-check.md`](../../../plan/03-reality-check.md) flags weeks 26–30 as the
  structural attrition risk, and this is one of the two projects it names: valuable,
  unglamorous, arriving after the novelty is gone. The failure mode is motivational, not
  technical, and the symptom is a week that quietly produces nothing. → look backwards, not
  forwards: with around a dozen public repos behind you, re-read your week 1 README and take
  the delta as evidence. Week 33's buffer is for publishing, not catching up.
- **A stampede demo burns metered cache operations fast** — the ceiling is the thing to
  check in [`../verified/`](../verified/) before you start, and to cap your runs against.

## The interview angle

One of the highest-yield system-design reps in the plan: real answers on cache invalidation,
the thundering herd, what a CDN actually does versus what people think it does, and eviction
under memory pressure. Resume line: *one endpoint served at four cache layers, with measured
hit rates, latencies and a fixed stampede.* The follow-up is "why not write-through?" — and
the honest answer is that you cut it: it buys consistency you did not need on a read-heavy
endpoint and would have doubled the build.

## Scope discipline

**Out of scope** — no write-through or write-behind (a second consistency model, on an
endpoint that is almost all reads); no distributed invalidation protocol (a multi-week
project of its own); no CDN configuration beyond the Cache API (dashboard work, and it does
not survive in a README).

**Stretch** — plant a deliberate cache-invalidation bug and write the test that catches it.
Only once the ship checklist is green; a stretch goal that eats the ship is a failure, not
an upgrade. Naming and licensing for the open-source cache you discuss are settled in the
newest audit in [`../verified/`](../verified/).
