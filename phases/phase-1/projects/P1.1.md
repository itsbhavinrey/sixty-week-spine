# P1.1 — `pgtour`

> Twelve analytical questions against a real public dataset, answered in SQL, with every query's plan and the index that made it fast.

**Phase 1** · ships week 4 · Neon free + Cloudflare Pages · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P1.1`

## Why this one

Someone has a messy public dataset, twelve questions about it and no analyst. This answers them
in SQL and publishes the plan behind each answer. It opens the phase on the spec's reordering
argument: SQL and wire protocols come before any framework, and SQL only gets learned while
there is no ORM to hide behind. The cheapest messy dataset is the registry dump
[`P0.2`](../../phase-0/projects/P0.2.md) already pulls — real nulls, duplicate names, date gaps
— and [`P1.2`](P1.2.md) designs a schema over that same data, which is harder if you have never
read a plan for a query over it.

## What you'll be able to do after

- You will have written window-function queries and can explain `PARTITION BY` and the frame
  clause with nothing in front of you.
- You will have read `EXPLAIN (ANALYZE, BUFFERS)` on your own queries and can point at which
  node an index changed, and by how much.
- You will have chosen indexes and can name what each costs on write, not only what it saves,
  and say why a CTE, a subquery and a join return the same rows at different cost.

## Where you'll get stuck

- **Window functions — the spec flags these as the wall.** Right shape, wrong numbers, because
  the default frame is not the one you assumed and the partition is not the group you meant →
  write the partition as a plain grouped query and diff it row by row. Budget the extra hours
  the spec asks for and **do not let the 2-hour rule fire here**: this struggle is the point.
- **Your index appears to do nothing.** The planner picks a sequential scan because on few rows
  it is cheaper, and because stats are stale → load enough rows to make the choice real,
  `ANALYZE`, then read the row estimates before blaming the index.
- **You run out of week.** DSA starts underneath this project, one a day, and
  [`plan/03-reality-check.md`](../../../plan/03-reality-check.md) calls it the plan's
  highest-attrition item. Nine of fifteen hours are build hours; size the table above to nine.

## The interview angle

This is the ten-minute SQL screen most India product-company loops open with: second-highest
per group, running totals, gaps and islands. The system-design rep is index selection as a
read/write trade-off — you can argue for an index and state its cost. Resume line: *twelve
analytical SQL queries over a messy public dataset, each with its plan and the index that made
it fast.* The follow-up is what happens at a hundred times the rows; partitioning is out of
scope here, so describe it, do not claim it.

## Scope discipline

**Out of scope** — no ORM (the entire point), no application layer, no charts library beyond
something trivial, no data-cleaning pipeline. The mess is a feature; cleaning it eats both
weeks.

**Stretch** — one query genuinely faster as a lateral join than as a subquery, with the plans
that prove it. Only after the ship checklist is green.
