# P1.4 — `sse-vs-ws`

> The same live counter built three ways - polling, SSE, WebSocket - with the bytes and latency to show when each one is the right answer.

**Phase 1** · ships week 8 · Cloudflare Workers + Durable Objects · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P1.4`

## Why this one

"Polling, SSE or a WebSocket?" usually gets answered by habit, and the three options get
compared with adjectives instead of numbers. This builds the identical live counter three times
and measures it, so the comparison is bytes and latency rather than taste. It closes the
phase's argument that wire-protocol literacy gates what comes later: the whole AI streaming
layer starts at [`P6.1`](../../phase-6/projects/P6.1.md) `streamgate`, which relays tokens over
SSE, and having measured all three here makes that a design decision you can defend rather than
a coin flip — the reconnection behaviour you observe is exactly what a token relay must
survive. It comes last because it needs the header work in [`P1.3`](P1.3.md): a stream a proxy
buffers is a header problem before it is a transport problem.

## What you'll be able to do after

- You will have implemented all three transports and can say which direction each carries data,
  how each reconnects, and which one a corporate proxy breaks.
- You will have measured bytes and p50/p99 latency on your own demos and can quote your own
  numbers instead of a rule of thumb.
- You will be able to explain why LLM APIs stream over SSE rather than WebSockets — request
  shape, retry semantics, infrastructure cost — from having built both.
- You will have held connection state in a Durable Object and can say what a single addressable
  coordinator solves that a stateless worker cannot.

## Where you'll get stuck

- **Your SSE stream arrives in one lump at the end.** Something between you and the browser is
  buffering, usually because the response is compressed or the content type and flushing are
  not what a stream needs → read the response headers first. This is [`P1.3`](P1.3.md) paying
  for itself, and it is a header fix, not a rewrite.
- **Latency numbers that measure your own clock.** Comparing a client timestamp against a
  server timestamp measures clock skew → measure round trips from one clock, state the method
  in the README, and treat the gap between transports as the result rather than the absolute
  values.
- **Reconnection looks fine because you never really broke it.** Closing a tab is not a dropped
  network, and each transport fails differently → break the connection at different layers and
  record what you actually did, so the demo is honest.
- **State in the wrong place.** Two tabs disagreeing means the count lives in the worker rather
  than the coordinator → keep the number in the Durable Object and let every transport read
  that one. If its lifecycle is still fighting you at two hours, the 2-hour rule applies: one
  connection, one increment, nothing else.

## The interview angle

This is the AI-backend question asked directly: why does every LLM API stream over SSE and not
WebSockets? You answer with a measurement and a reconnect demo instead of an opinion. The
system-design rep is fan-out and connection state — where state lives, what happens when a
client vanishes, what a coordinator costs. Resume line: *the same live counter over polling,
SSE and WebSockets, with measured bytes and latency and a reconnection demo for each.* The
follow-up is behaviour at thousands of concurrent connections; the honest answer is that load
testing is a phase 5 project and this measures cost per transport, not scale.

## Scope discipline

**Out of scope** — no chat app (the counter is the point: identical payload across three
transports), no auth, no persistence beyond the coordinator, no scaling test. Scaling belongs
to phase 5 and would swamp the week.

**Stretch** — a fourth panel on server push's corpse: what it promised, and why it was removed.
Only after the ship checklist is green.
