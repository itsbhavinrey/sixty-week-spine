# P1.2 — `driftwatch` · driftwatch layer 2

> The CLI grows a memory: scans, packages, versions and findings persisted in a schema that can answer 'what changed since last week?'

**Phase 1** · ships week 5 · Neon free · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P1.2`

## Why this one

Layer 1 tells you how stale your dependencies are today, then forgets, so the question a user
actually asks — what changed since last week? — cannot be answered. This layer is the memory: a
normalized schema (`orgs`, `repos`, `scans`, `packages`, `package_versions`, `findings`),
migrations that take an empty database to that shape, and one query that diffs two scans. It
depends on layer 1, [`P0.2`](../../phase-0/projects/P0.2.md) — no history to persist until the
CLI produces scans — and layer 3, [`P2.2`](../../phase-2/projects/P2.2.md), puts an API over
this schema. Schema before application code is deliberate: the shape is cheap to change now and
expensive once handlers, pagination and a public contract are written against a wrong one.

## What you'll be able to do after

- You will have normalized a schema yourself and can defend, table by table, which duplication
  you removed and which you kept.
- You will have written migrations that run clean from empty and can say why forward-only beats
  hand-edited tables.
- You will be able to model the same package at different versions over time, say where the
  natural key ends and a surrogate key starts, and read the plan of the diff query you wrote.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | ERD on paper, keys and cardinalities marked | first hour | Every relation has a cardinality and a reason |
| 2 | Migration runner chosen, ADR written | ~2 hrs | Empty database to full schema in one command |
| 3 | Six tables, with constraints that reject bad rows | ~3 hrs | A finding with no scan fails; the same scan twice fails |
| 4 | CLI writes scans to Neon behind a flag | ~2 hrs | Two runs leave two scans you can see in `psql` |
| 5 | The diff query, plus its captured plan | ~2 hrs | It names added, removed, upgraded, newly-stale |

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green,
migrations run clean from empty, and the README carries the ERD, the normalization decisions
and what you denormalized on purpose, and the diff query with its plan. Someone else can drop
the database, migrate, scan twice, diff.

## Where you'll get stuck

- **The version table fights you.** A package version is a fact about the world with a publish
  time, not an attribute of your scan, and the first draft staples it to the scan row → settle
  whether `package_versions` is scan-scoped or global before writing it, in the ADR.
- **The diff query grows to a page** of `LEFT JOIN` and `COALESCE` nobody can read → make it a
  full outer join between two CTEs, one per scan, so each row states what happened. Still
  fighting at two hours: the 2-hour rule applies — two packages per scan, then grow it.
- **Migrations only work forwards from your machine.** They pass because your database already
  has the previous shape, and fail from empty on an ordering or default you never noticed →
  drop-and-migrate-from-empty is the command you run every time, not the one before shipping.

## The interview angle

"Design the schema" is a standard India product-company round, and this is the rep: six tables
from memory, the normal form you stopped at named, one denormalization justified by the query
it serves. The system-design rep is temporal data. Resume line: *normalized Postgres schema
with forward-only migrations backing a dependency-scan history, with a single-query diff
between any two scans.* The follow-up is what the diff costs as scans accumulate;
snapshot-per-scan is the simple choice and you can price it.

## Scope discipline

**Out of scope** — no API (that is layer 3), no auth, no UI, no ORM. Any of them pulls the week
away from schema design, the only thing this layer teaches. Constraints belong in the schema,
not in TypeScript.

**Stretch** — temporal validity on `package_versions` using Postgres range constraints, so
overlapping periods are rejected by the database. Confirm the constraint form you want is
available in [`../verified/`](../verified/) first, and only after the checklist is green.
