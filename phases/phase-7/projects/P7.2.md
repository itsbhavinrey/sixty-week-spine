# P7.2 — `grpc-pair`

> Two services, one .proto contract, a streaming method, generated stubs in the repo, and a load test.

**Phase 7** · ships week 46 · Render free + Cloudflare Pages · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P7.2`

## Why this one

Everything you have shipped so far talks over REST, and the layer mid-level backend interviews ask
about — service to service, inside the perimeter — is not REST. This is the smallest honest version
of that layer: one schema file both services generate from, a server-streaming method so the wire
behaviour is not just request/response, stubs committed so a reviewer can see what codegen produced,
breaking-change detection in CI, and load-test numbers next to the equivalent REST endpoint. It sits
in week 46 because the typed-contract instinct came from
[`P2.1`](../../phase-2/projects/P2.1.md) and the load-testing habit from
[`P5.4`](../../phase-5/projects/P5.4.md); with both in hand this is a week, not a fortnight. Phase 7
buys vocabulary and reps, not spine features — `driftwatch` is untouched between
[`P6.7`](../../phase-6/projects/P6.7.md) and [`C1`](../../phase-8/projects/C1.md) — and this is
squarely vocabulary. It is also the only project of the five with a live URL.

The deploy target breaks the plan's Cloudflare default, and the protocol forces it: a streaming gRPC
method needs a process that holds a connection open and terminates the multiplexed transport itself,
which the edge-function model the rest of the plan uses does not host. So the two services run as
free Render web services — a container, no card — and Cloudflare Pages serves the static browser
client. Those instances sleep when idle, so the first request after a quiet spell pays a cold start;
put that in the README rather than hiding it, and check [`../verified/`](../verified/) for the
current shape of that tier before planning the demo around it.

## What you'll be able to do after

- You will have written a schema-first contract yourself and can explain what field numbers mean for
  wire compatibility, and which edits are safe against a deployed peer.
- You will have implemented and consumed a server-streaming method and can say what it gives you
  that polling does not, and where it is worse than the event streaming you built earlier.
- You will have made CI fail on a breaking contract change and can explain why that check belongs to
  the schema, not to a review convention.
- You will have p50/p99 numbers for one operation over two protocols and can name what the
  difference is made of.

## Where you'll get stuck

- **It works between your two processes and not from the browser.** Browsers cannot speak the raw
  protocol; the client path needs the browser-compatible transport and a matching server handler →
  build the browser client against that transport from the first commit rather than porting a
  working native client later.
- **Generated code drifts from the schema.** Someone edits a stub, or the local generator differs
  from CI's → make regeneration a build step with a no-diff check, so drift is a red build.
- **The streaming method hangs at the end.** Streams need an explicit completion, and a half-closed
  connection looks identical to a slow server → assert on stream termination in a test, not by
  watching the UI. An hour into a hang with no reproduction, reduce to a three-message stream with no
  application logic; the 2-hour rule applies.
- **Load-test numbers say nothing.** A sleeping instance makes the first run look terrible → warm
  both endpoints, run the same shape against both, and report the cold start as its own fact.

## The interview angle

This answers "how do your services talk to each other" with a repo instead of an opinion, and the
follow-up about schema evolution — what happens when one side deploys first — has a real answer
because CI already refused one. The system-design rep is the fan-out design in
[`P7.5`](P7.5.md), where the streaming-versus-polling choice recurs. Resume line: *two services on
one schema-first contract with a server-streaming method, committed generated stubs, a
breaking-change gate in CI, and a load-test comparison against REST.* The next question is usually
identity between services; the honest answer is that it was scoped out, and you know what it adds.

## Scope discipline

**Out of scope** — no service mesh, no mutual TLS, no more than two services, no browser
compatibility work beyond the one supported transport. A third service teaches nothing the second
did not, and mesh work is a phase, not a week.

**Stretch** — bidirectional streaming, or workload identity between the two services. After the
checklist is green only.
