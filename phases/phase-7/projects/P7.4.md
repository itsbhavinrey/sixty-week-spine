# P7.4 — `k8s-workload`

> driftwatch packaged for Kubernetes at the workload level - the layer you'd actually be asked about.

## Why this one

Be clear about what this is worth. [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) moved
Kubernetes to the end of the plan for a stated reason: "70–80% of K8s roles are senior; it earns you
nothing at the mid-level bar and costs 2 weeks. It's here only for interview vocabulary." That is
the honest framing. You are not learning to operate a cluster; you are learning to hold a
conversation about one — enough that a manifest walkthrough does not bluff, and enough that
"readiness probe" means something you have watched work. Phase 7 adds no layer to the spine —
`driftwatch` is untouched between [`P6.7`](../../phase-6/projects/P6.7.md) and
[`C1`](../../phase-8/projects/C1.md) — and this is that trade at its starkest: pure vocabulary,
deliberately time-boxed. It sits in weeks 48 and 49 because it needs the container images from
[`P4.1`](../../phase-4/projects/P4.1.md) and the health and metrics endpoints from
[`P4.3`](../../phase-4/projects/P4.3.md); without those, probes and autoscaling have nothing real to
read.

There is no free managed cluster, so there is no live URL. A local cluster in a container plus
`make demo` and a recorded install is the proof, and the roadmap calls that completely legitimate.
Which controller and API surface to target is exactly the kind of fact that rots — the default that
every tutorial installs has been retired once already — so read
[`../verified/`](../verified/) before you write a manifest, and treat
[`../topics.md`](../topics.md) as the list of things to re-check.

## What you'll be able to do after

- You will have written the workload objects yourself — deployment, service, routing, config and
  secret, requests and limits — and can explain what each one is for in a sentence.
- You will have configured liveness and readiness separately and can explain what breaks when a
  service reports ready before it is, and what a wrong liveness probe does under load.
- You will have watched an autoscaler add and remove replicas and can name the signal it reacted to
  and the lag between signal and scale.
- You will have packaged the whole thing as a chart and can explain what belongs in values and what
  does not.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | Local cluster up, image loaded, one pod running | first hour | `kubectl` shows your own image serving traffic in-cluster |
| 2 | Deployment, service, routing, config and secret | ~3 hrs | The app is reachable through the router, configured from outside the image |
| 3 | Probes, requests and limits, least-privilege access | ~2 hrs | A deliberately unhealthy pod is replaced; the app runs without cluster-wide rights |
| 4 | Autoscaling, with a load run that triggers it | ~2 hrs | A scaling event is visible in the recording |
| 5 | Chart, then a clean install on a fresh cluster | ~2 hrs | Delete the cluster, create it, install once, no manual step |

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green, the chart
installs clean on a cluster created from nothing, and the README carries the manifest walkthrough, a
recording of the install and one of a scaling event.

## Where you'll get stuck

- **The cluster pulls your image from the internet and fails.** A local cluster does not see your
  local image store by default, so a perfectly built image reports as unpullable → load the image
  into the cluster explicitly as a step in `make demo`, and pin the pull policy so it does not go
  looking.
- **Readiness passes before the app can serve.** A probe pointed at a route that answers before
  dependencies are connected sends traffic into a cold process → point readiness at something that
  actually checks the dependency, and keep liveness dumber than readiness on purpose.
- **The autoscaler never scales.** It needs a metrics source in the cluster and resource requests to
  compute against; missing either produces no error, just a stubborn replica count → verify requests
  are set and metrics are being served before touching thresholds.
- **You start operating instead of packaging.** Cluster internals, mesh, operators and networking
  are a rabbit hole with no floor → this project has the tightest scope discipline in the phase. Two
  hours on anything below the workload level means the 2-hour rule fires and you write it down as
  out of scope instead. The goal is to talk about this, not to run it.

## The interview angle

The realistic question is a walkthrough: "here's a service, what would you need to run it on
Kubernetes." You can answer it object by object and say what each is for, including why you chose
the routing API you did. The system-design rep is capacity planning — requests, limits and
autoscaling thresholds are the same arithmetic as the scale assumptions in [`P7.5`](P7.5.md).
Resume line: *`driftwatch` packaged as a chart with probes, resource limits, least-privilege access
and autoscaling, installing clean on a fresh local cluster.* The follow-up is almost always about
production concerns you have not met — multi-cluster, upgrades, cost — and the right answer names
the limit directly: this is workload-level knowledge, deliberately, and you know which questions are
above it. Applications start in week 57, eight weeks out — this answer gets used soon.

## Scope discipline

**Out of scope** — no cluster bootstrapping by hand, no operators, no service mesh, no managed
cluster, no cluster networking internals. Each is senior-track work that costs weeks and adds
nothing at the bar you are interviewing for.

**Stretch** — a policy that rejects a container running as root, with the rejection recorded. Cheap,
and it demonstrates the security instinct. Only after the checklist is green.
