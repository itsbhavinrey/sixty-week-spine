# P2.4 — `driftwatch` · driftwatch layer 3b

> The driftwatch test suite: unit tests that run in 2 seconds and integration tests that run against a real Postgres in CI.

**Phase 2** · ships week 14 · GitHub Actions + Neon branches · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P2.4`

## Why this one

This layer adds no endpoints (`plan/01-roadmap.md` calls it `test-harness`). It adds the
thing that lets every later layer change `driftwatch` without silently breaking it: a suite
that runs against a real Postgres rather than a mock of one, on every push. It goes
immediately after [`P2.2`](P2.2.md) because layer 3 is the first layer with enough surface
that a refactor can break something you would not notice, and before phase 3 because
[`P3.4`](../../phase-3/projects/P3.4.md) enforces authorization at the query layer — you want
tests underneath those rules, not written after them. It leans on
[`P1.2`](../../phase-1/projects/P1.2.md) for the migrations the integration tests run.

## What you'll be able to do after

- You will have split unit from integration tests by what they touch and can defend the line.
- You will have built an ephemeral database per CI run — created, migrated, tested,
  destroyed — and can explain why that beats a mocked repository layer.
- You will have a coverage gate that fails the build and can say what the number does and
  does not tell you.
- You will have diagnosed a flaky test to its cause rather than retrying it.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | Unit tests on the pure parts: cursor encoding, staleness heuristic, error mapping | first hour | The suite is fast enough that you leave it running while you type |
| 2 | Integration tests locally against a database branch you create by hand | a third | Migrations run from empty, seed, assert, tear down |
| 3 | Wire it into Actions: a branch per run, plus the coverage gate | a third | A pull request goes green; dropping coverage turns it red |
| 4 | Write one flaky test on purpose, diagnose it, fix it, write it up | remainder | The post-mortem names the cause, not the retry that hid it |

**Definition of done** — a green CI run on a pull request whose log shows a database branch
created, migrated, tested and destroyed, and a demonstrated red run when coverage drops. Then
the ship checklist in [`../README.md`](../README.md) is green.

## Where you'll get stuck

- **Branches survive their jobs** — a teardown written as a normal step does not run after a
  failure, so every failed run leaks a branch until you hit the ceiling (that ceiling is the
  thing to check in [`../verified/`](../verified/) before you start) → an always-run cleanup
  step, plus a sweep for the ones you leaked while learning this.
- **Passes locally, fails in CI, differently each time** — tests sharing database state let
  execution order decide the outcome. This is also your flaky test, so use it rather than
  inventing one → give each test its own rows, or a transaction rolled back per test, and
  write the diagnosis while you are still annoyed. That is when it is honest.
- **CI cannot reach the database** — credentials and connection settings behave differently
  inside a runner, and the symptom is a wall of failed tests instead of one clear error. Fire
  the 2-hour rule immediately: one workflow, one step, one query. Do not debug plumbing
  through the full suite.
- **The coverage gate becomes a number you game** — chasing a percentage rewards testing
  trivia → keep the gate, but the section an interviewer reads is the pyramid with counts.

Week 14 is the last shipping week of phase 2 and week 15 is the buffer;
[`plan/03-reality-check.md`](../../../plan/03-reality-check.md) says you will need all five
buffer weeks. Two spine layers plus two spurs make this the densest stretch before phase 6,
so plan on this taking part of the buffer rather than treating that as failure.

## The interview angle

"How do you test code that talks to a database" comes up in most backend loops, and "a
database branch created per CI run and destroyed after" is a materially better answer than
"we mock the repository". The post-mortem answers "tell me about a bug you could not
reproduce". The system-design rep is ephemeral environments: what test isolation costs, and
why a shared test database eventually produces tests nobody trusts. Resume line: *a test
suite with real-Postgres integration tests on an ephemeral database per CI run, and a
coverage gate that fails the build.* The follow-up is "what about end-to-end" — honest
answer: cut, and the real smoke test is the deploy itself.

## Scope discipline

**Out of scope** — no browser end-to-end tests: a second toolchain and a second class of
flake in a week that already has one. No mutation testing. No load testing; that needs the
observability from phase 4 to be worth reading, which is why it sits in phase 5.

**Stretch** — smoke tests in a browser driver against the deployed Worker. Only after the
ship checklist is green.
