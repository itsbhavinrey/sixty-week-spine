# P6.1 — `streamgate`

> A provider-agnostic LLM gateway that streams, fails over, meters every token, and refuses to bankrupt you.

**Phase 6** · ships week 34 · Cloudflare Workers + D1 · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.1`

## Why this one

Anyone putting a model call into a product needs it to stream, to survive the provider being
down, and to stop before the bill does something stupid. This is that shim, and every other
project in the phase calls it — build it once here or build it badly four times. It opens the
phase because it assumes almost nothing new: the token relay *is* an SSE relay, and you already
measured SSE against the alternatives in [`P1.4`](../../phase-1/projects/P1.4.md), so the work
is all in the failure handling. [`plan/03-reality-check.md`](../../../plan/03-reality-check.md)
sanctions pulling it forward into week 33's buffer if the month-7 wall bites — the one place in
the plan where breaking dependency order is approved, because an LLM win arrives exactly when
momentum is gone and nothing downstream cares. [`P6.2`](P6.2.md) runs its prompts through this,
[`P6.4`](P6.4.md) streams its answers through it, and [`P6.7`](P6.7.md) can only measure a cost
cut because this wrote the ledger.

## What you'll be able to do after

- You will have written a token relay yourself and can explain why model APIs stream over SSE
  rather than WebSockets, and what a proxy in between does to that.
- You will have built a fallback state machine across several hosted providers and can draw it,
  including the case the spec cares about most: a provider that fails *after* you have already
  emitted tokens to the client.
- You will have metered token counts and cost per request into D1 and can explain why your
  count and the provider's invoice disagree.
- You will have a budget kill-switch and can argue whether it should fail open or fail closed,
  which is a design position, not a default.

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green, there is
a live streaming endpoint, and the README carries the fallback state machine, the
cost-per-thousand-requests table across the providers, and a recording of the kill-switch
tripping. Someone else can watch tokens arrive and then watch the gate refuse.

## Where you'll get stuck

- **Streaming works locally and arrives as one block deployed.** Something between you and the
  client is buffering, or you are awaiting the whole upstream body before writing → stream the
  upstream response through rather than reading it, and check the relay with `curl` before
  blaming the browser.
- **Failover after the first token.** You cannot silently retry: the client already has half an
  answer in a different voice. Decide the policy — abandon, restart with a visible marker, or
  degrade — and write it down. This is the decision the project exists to make.
- **Your token count does not match the provider's.** Counting is provider-specific and usage
  numbers arrive at the end of the stream, or not at all on a failed run → record the provider's
  reported usage as the source of truth and treat your own count as an estimate.
- **The kill-switch leaks.** Concurrent requests each read the budget before any of them writes,
  so all of them pass → decide up front whether you need a serialized check, and say so.

If one of these eats more than two hours the 2-hour rule in
[`plan/01-roadmap.md`](../../../plan/01-roadmap.md) fires: falsifiable sentence, smallest
reproduction, then the provider's own docs. The providers this routes to are on no-cost plans
that change quietly, and one of them uses free-plan content to improve its own products — check
[`../verified/`](../verified/) before you start, put that warning in the README, and never route
real user data through that path.

## The interview angle

This answers "how would you make an LLM call production-safe?" without hand-waving — the question
that separates wrapper-builders from backend engineers. The system-design rep buried in it is a
metered gateway in front of an unreliable upstream: quotas, per-tenant accounting, graceful
degradation. Resume line: *a provider-agnostic streaming LLM gateway with automatic fallback,
per-request token and cost accounting, and a hard budget kill-switch.* The follow-up a good
interviewer asks is what happens on a mid-stream failover; the honest answer is the policy you
chose and the one you rejected.

## Scope discipline

**Out of scope** — no semantic caching (that is [`P6.7`](P6.7.md), and it needs a cost baseline
this project has not produced yet), no fine-tuning, no self-hosted inference (it needs a GPU you
do not have and cannot rent at zero cost), no chat UI beyond a minimal test page. The UI is the
easiest place to lose a week here.

**Stretch** — accept a drop-in-compatible request format so other tools can point at it. Only
after the ship checklist is green.
