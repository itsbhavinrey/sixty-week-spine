# P6.6 — `upgrade-agent`

> An agent that reads your changelog RAG, decides an upgrade is safe, opens a real PR, and waits for a human to say yes.

**Phase 6** · ships week 42 · GitHub App + Cloudflare Workers · difficulty High
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.6`

## Why this one

Dependency bots open pull requests that nobody can evaluate, because the bot has no idea what
the upgrade breaks. This one reads the retrieval layer first, cites the changelog evidence in
the pull request body, and then stops and waits for a person. It is the most product-shaped
thing in the plan: installed on a repo, it does work someone would otherwise do by hand. It
lands second-to-last because it needs three things finished — [`P6.4`](P6.4.md) for evidence,
[`P6.5`](P6.5.md) for a tool surface a loop can call, and [`P6.3`](P6.3.md) for any way at all to
tell a good decision from a plausible one. It is one week for a hard project, which is
survivable only because week 43 behind it is a buffer week and [`P6.7`](P6.7.md) is deliberately
small. The stretch — a merged pull request on someone else's repo — is worth more in an
interview than most portfolio projects.

## What you'll be able to do after

- You will have written a reason-act loop yourself and can explain why a hard tool allowlist is
  an architectural decision rather than a safety afterthought.
- You will have put a mandatory human checkpoint in front of every write and can argue where the
  line between "agent decides" and "human approves" belongs.
- You will have an immutable audit log of every tool call and can explain what you would need it
  for when the agent does something surprising.
- You will be able to say how you evaluate an agent's *decisions* rather than its prose, because
  [`P6.3`](P6.3.md) gave you a way to score them.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | GitHub App installed on a throwaway repo | first hour | A webhook arrives, signature verified, and you can read a file |
| 2 | Reason-act loop with the allowlist and a step cap | ~3 hrs | It reads a manifest, queries `driftwatch`, and proposes one upgrade |
| 3 | Pull request body built from cited evidence | ~2 hrs | Every claim in the body links to a changelog line |
| 4 | Human checkpoint + kill switch | ~2 hrs | No write happens without an explicit approval; the switch stops a run mid-loop |
| 5 | Immutable audit log of every tool call | ~2 hrs | A run can be reconstructed after the fact from the log alone |
| 6 | Scored against `evalbench`, then a real pull request | ~2 hrs | Its upgrade-safety calls are measured, not asserted |

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green, and the
proof is a real pull request the agent opened on a real repo, linked from the README, alongside
the agent-loop diagram, the tool allowlist with the reasoning for each entry, and the audit-log
format. Someone else can read the pull request and check the evidence without trusting the agent.

## Where you'll get stuck

- **It acts confidently on a repo it misread.** Workspaces, monorepos, overrides and peer ranges
  mean the manifest you parsed is not the dependency graph that resolves, so the agent proposes
  an upgrade that is already pinned elsewhere → treat the resolved tree as the source of truth,
  not the manifest, and make the pull request body state what it read. The checkpoint exists so
  a human catches this class; the citations exist so catching it is cheap.
- **You cannot tell a good pull request from a plausible one.** The prose is fluent, the reasoning
  reads fine, and you have no idea whether the decision was right. This is the failure mode the
  phase spent two weeks preparing for → score the decision against the golden set from
  [`P6.3`](P6.3.md): was the upgrade actually safe, yes or no. Never judge the loop by how good
  the write-up sounds.
- **The loop loops.** A failed test or an ambiguous tool result sends it round again, retrying
  and spending tokens with nothing changing → a hard step cap, a cap on repeated identical calls,
  and the budget kill-switch from [`P6.1`](P6.1.md). An agent without a step cap is an incident.
- **Webhook and app-permission plumbing.** Signature verification, installation tokens and the
  permissions the app requested are all things that fail identically-looking ways, and locally
  versus deployed differ because the callback is registered once → this is where the 2-hour rule
  from [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) fires. Smallest reproduction against
  one throwaway repo, then the platform's own docs.

## The interview angle

Everyone claims to have built an agent; almost nobody can describe its guardrails. This lets you
answer "how do you let an agent write to a repo?" with sandboxing, a per-tool allowlist, a human
checkpoint on the sensitive action, a kill switch and an audit trail — the set the current
security literature actually asks for. The system-design rep buried in it is designing for blast
radius: what is the worst thing this can do, and what makes that impossible rather than
unlikely. Resume line: *a GitHub App agent that proposes dependency upgrades with cited
changelog evidence, behind a hard tool allowlist and a mandatory human approval.* The follow-up a
good interviewer asks is whether you would auto-merge; the honest answer is never, and the reason
is that an agent's confidence is uncorrelated with its correctness — which you can show, because
you measured it.

## Scope discipline

**Out of scope** — no multi-agent, no auto-merge ever, no agent-to-agent protocol, no
long-running orchestration. Orchestration in particular is a later phase, and reaching for it
here replaces one week of guardrails with three weeks of infrastructure.

**Stretch** — run it against a real open-source repository and get the pull request merged. Only
after the ship checklist is green; a merged upstream pull request is the single highest-value
artifact available in this phase.
