# P6.2 — `promptlab`

> Prompts as versioned, tested files - with an injection suite that fails the build.

**Phase 6** · ships week 35 · Cloudflare Workers + GitHub Actions · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.2`

## Why this one

A prompt in a product is a string that changes behaviour for every user and lives outside code
review. This drags it back in: prompts become files with frontmatter and a version, a golden set
of expected behaviours, and a red-team suite that fails CI when a change reopens a hole. It sits
here because it needs somewhere to run prompts — [`P6.1`](P6.1.md), shipped last week — and
because it has to land before retrieval: [`P6.4`](P6.4.md) pulls third-party changelog text into
the context window, which makes indirect injection a real surface in your own system rather than
a hypothetical from a talk. It also gives [`P6.3`](P6.3.md) something addressable to score, since
you cannot regression-test a prompt with no version. The four-layer context stack you make
explicit here — system, persistent, retrieved, working — is the structure every later project
fills in.

## What you'll be able to do after

- You will have written the four-layer context stack out as code and can say which layer a given
  piece of text belongs in, and what breaks when retrieved content is pasted into the system
  layer.
- You will have landed direct injection, indirect injection through retrieved content, and
  system-prompt extraction against your own prompts, and can describe what each one exploits.
- You will have a CI job that fails on a prompt change and can explain how you made a
  non-deterministic check stable enough to gate a merge.
- You will be able to map your own findings onto the current edition of the OWASP LLM Top 10
  rather than quoting the list — the spec warns that the source syllabus cites a stale edition,
  and [`../verified/`](../verified/) says which one is live and what moved.

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green and the
README carries the four-layer context diagram, the three injections that worked before your
defenses and fail after, and the screenshot of CI refusing the bad prompt. The before/after pair
is the whole artifact; a suite that has never caught anything proves nothing.

## Where you'll get stuck

- **An injection "fails" for the wrong reason.** The model declined because of its own safety
  training or because the phrasing confused it, not because your defense worked → run each
  attack several times, score it as a rate rather than a boolean, and keep the undefended
  baseline in the repo so you can tell the difference.
- **CI is flaky and you start ignoring it.** You are asserting on generated prose, which varies
  run to run → assert on structure and markers (did the secret string appear, did the tool get
  called), not on wording, and pin the sampling settings in the frontmatter.
- **System-prompt extraction cannot be fully stopped.** You will spend hours trying to close it
  before reading that it is a mitigation problem, not a prevention one → this is where the
  2-hour rule from [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) fires. Write the honest
  limitation in the README and treat the system prompt as non-secret by design.
- **The layer boundary collapses under convenience.** Concatenating everything into one string is
  easier, and then retrieved text has system-layer authority → keep the layers separate all the
  way to the call, and make the assembler the only place they meet.

## The interview angle

Prompt injection is unsolved, and interviewers use it to find out whether you know that. This
lets you answer "how do you defend against prompt injection?" with a demonstration and a
limitation instead of a list. The system-design rep buried in it is trust boundaries: which
input is attacker-controlled, and what authority does it inherit. Resume line: *prompts as
versioned, reviewed files with a red-team suite covering direct and indirect injection, gating
CI.* The follow-up a good interviewer asks is what happens when injected text arrives through
retrieval at runtime rather than from your fixtures; the honest answer is that the suite tests a
fixed corpus and the runtime defense is layer separation plus output handling, not a filter that
catches everything.

## Scope discipline

**Out of scope** — no prompt-optimization automation, no declarative prompt-compilation
framework, no multi-turn conversation management. Each of those is a project on its own, and
automated optimization in particular would consume the week and leave you without the suite,
which is the part that fails the build.

**Stretch** — add a second red-team tool and compare what each one catches that the other misses.
Only after the ship checklist is green.
