# P6.3 — `evalbench`

> A golden dataset, an LLM judge, and a CI job that tells you whether your last prompt change made things worse.

**Phase 6** · ships week 37 · GitHub Actions + Pages · difficulty Medium
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.3`

## Why this one

This is the reordering that defines the phase. The table in
[`plan/01-roadmap.md`](../../../plan/01-roadmap.md) puts evals before RAG for one reason:
*without a golden dataset you cannot tell whether your reranker helped — building RAG first means
rebuilding it.* Build the ruler before the thing you measure. So this lands in weeks 36–37, two
weeks before [`P6.4`](P6.4.md), and the dataset is not generic: it is hand-curated examples of
`driftwatch`'s own "what breaks if I upgrade?" task, which means the moment retrieval exists it
already has a score. It needs [`P6.2`](P6.2.md) first, because a versioned prompt is what a
regression test regresses against. And it is the thing [`P6.6`](P6.6.md) leans on hardest: an
agent that opens pull requests needs some way to tell a good decision from a plausible one, and
this is the only project in the plan that buys that.

## What you'll be able to do after

- You will have hand-curated a golden set and can defend why each example is in it and what it is
  meant to catch — the part everyone skips and the part that makes the numbers mean anything.
- You will have written a judge rubric and can explain how an LLM judge fails: position bias,
  length bias, self-preference.
- You will have measured that bias yourself by running the same pairs in reversed order and
  reporting the delta, rather than citing a paper that says it exists.
- You will have a CI job that blocks a prompt change on a score drop, and published results, so
  "did this help?" is a number instead of an argument.

## Build plan

| # | Milestone | Roughly | Done when |
|---|---|---|---|
| 1 | Ten examples by hand, in a file | first hour | Each has an input, an expected behaviour, and a reason it exists |
| 2 | The full golden set | ~5 hrs | Enough examples to move a score, all hand-checked. **End of week 36** |
| 3 | Judge rubric + single-answer scoring | ~3 hrs | Two known-bad answers score below two known-good ones |
| 4 | Pairwise comparison with Elo ratings | ~3 hrs | Ranking is stable across two full runs |
| 5 | Bias check: reversed order, length-matched pairs | ~3 hrs | The delta is measured and written down, whatever it says |
| 6 | GitHub Action + published results page | ~3 hrs | A prompt change opens a red pull request; the page shows scores over versions |

**Definition of done** — the ship checklist in [`../README.md`](../README.md) is green, the
results page is live, and the README carries the dataset construction method, the judge rubric
verbatim, the bias-check numbers, and a chart of scores across your recent prompt versions. The
observable end state: someone edits a prompt in a pull request and CI tells them it got worse.

## Where you'll get stuck

- **Curating examples by hand is slow and boring, and week 36 ships nothing.** That combination
  is the real risk here, not the code. You will be tempted to generate the dataset with a model,
  which quietly makes the ruler a reflection of the thing it measures → if you generate
  candidates, hand-check and hand-edit every one and say so. A smaller honest set beats a large
  synthetic one.
- **The judge prefers its own style.** Scores move when you swap answer order, or when one answer
  is simply longer and nothing about the content changed → run every pair both ways, report the
  disagreement rate, and length-match a subset. Finding bias is a result, not a failure.
- **Elo swings between runs.** With few comparisons per item the ratings are noisy → increase
  comparisons per pair before touching the rating maths, and report the comparison count next to
  the rating.
- **The CI job is too slow or too chatty to keep.** Every merge re-scores the whole set against a
  hosted model on a no-cost plan → run the full set on a schedule and a subset per pull request,
  and route it through the metered gateway from [`P6.1`](P6.1.md) so the run has a recorded cost.
  If the harness itself eats two hours the 2-hour rule from
  [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) fires — check
  [`../verified/`](../verified/) for which eval library is currently maintained rather than
  fighting one that is not.

## The interview angle

"How do you know your prompt change helped?" is the question most candidates cannot answer, and
published eval results put you in the smaller half of teams that run offline evals at all. The
system-design rep buried in it is regression testing a non-deterministic system: sampling,
thresholds, and what you gate a merge on when the output is never byte-identical. Resume line:
*a hand-curated golden dataset with an LLM-judge rubric, a documented judge-bias check, and a CI
job that blocks prompt regressions.* The follow-up a good interviewer asks is about inter-judge
agreement; the honest answer is that a second judge model was the stretch goal and you cut it to
keep the bias check.

## Scope discipline

**Out of scope** — no human-annotation platform, no RLHF, no fine-tuning, no evaluating models
you are not actually using. Each would turn a two-week project into a phase.

**Stretch** — add a second judge model and report inter-judge agreement. Only after the ship
checklist is green; the bias check matters more than a second opinion.
