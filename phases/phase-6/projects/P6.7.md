# P6.7 — `driftwatch` · driftwatch layer 7b

> Measured cost reduction on driftwatch's LLM spend, with the before-and-after numbers.

**Phase 6** · ships week 43 · Cloudflare Workers · difficulty Low
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.7`

## Why this one

Running the spine's retrieval layer costs something per scan, and the interesting engineering is
making that number smaller without making the answers worse. This layer applies the standard
ladder in order — caching stable prompt content, batching non-interactive scans, routing cheap
work to a cheap model and reserving the expensive one for synthesis, then semantic caching — and
measures the effect at each rung, quality included (`plan/01-roadmap.md` calls this layer
`costcut`). It lands last because it needs a real bill: [`P6.4`](P6.4.md) produced the workload,
[`P6.1`](P6.1.md) the ledger that makes a before/after honest, and [`P6.3`](P6.3.md) the quality
column, without which a cut cannot be told apart from a downgrade. It is the only
low-difficulty project in the phase and it sits in week 43, a buffer week — that is deliberate.
If the two hard projects before it ran long, this absorbs the slippage; if they did not, you
finish the phase holding the number that goes on the capstone's cost page in
[`C1`](../../phase-8/projects/C1.md).

## What you'll be able to do after

- You will have measured cost per scan at each rung of the ladder and can explain which rung paid
  and which one did nothing for your workload.
- You will have implemented prompt caching against a stable prefix and can explain why the order
  of your context layers determines whether it works at all.
- You will have routed between models by task and can defend the split — classification cheap,
  synthesis expensive — as a design position rather than a trick.
- You will be able to say why a cost cut that moves eval scores down is not a cut, with your own
  table as evidence.

## Where you'll get stuck

- **Your before and after are not comparable.** Cost per scan varies with the repository scanned
  and with how much retrieved text landed in the context, so the second measurement looks better
  for reasons unrelated to your change → fix the scan corpus and the retrieval configuration
  before the first row, and re-run the baseline at the end to prove nothing else drifted.
- **Prompt caching does nothing.** The cache needs a stable prefix, and your context assembler
  from [`P6.2`](P6.2.md) puts retrieved chunks — the part that changes every request — near the
  front → reorder the layers so the stable ones lead, then confirm hits in the ledger rather
  than assuming them.
- **The semantic cache returns the wrong answer confidently.** Two upgrade questions can be
  textually similar and semantically opposite, and a near-hit gets served as a hit → this is the
  rung to be most suspicious of; check it against the golden set, set the threshold from that
  measurement, and be willing to report that you removed it.
- **The batch path leaks into the interactive path.** Batched work trades latency for cost, which
  is fine for scheduled scans and unacceptable for someone waiting on an answer → keep two code
  paths, and put the tail-latency column in the table so the trade-off is visible.

Week 43 is a buffer. If a rung eats more than two hours the 2-hour rule from
[`plan/01-roadmap.md`](../../../plan/01-roadmap.md) applies, and the right move is to publish the
rungs that worked plus the measurement that shows why you stopped. A three-row honest table
ships; a four-row table you could not verify does not.

## The interview angle

Cost and latency engineering gets cited in promotion cases, not only in interviews, and almost
nobody in a mid-level loop can talk about it with their own numbers. This lets you answer "how
would you reduce the cost of an LLM feature?" as an ordered set of techniques with measured
effects and a quality guardrail. The system-design rep buried in it is the caching and routing
trade-off applied to a non-deterministic backend — the same ladder as
[`P5.1`](../../phase-5/projects/P5.1.md), one layer up. Resume line: *measured cost reduction on
a live retrieval workload through prompt caching, batching, model routing and semantic caching,
with eval scores reported alongside every step.* The follow-up a good interviewer asks is which
rung to skip; the honest answer names the one that did nothing for your workload, and why that
is workload-specific rather than general advice.

## Scope discipline

**Out of scope** — no self-hosting (it only makes sense at volumes you will never reach, and it
needs hardware the budget rules out), no quantization, no fine-tuning. Each is a rabbit hole that
would consume the buffer week this project is sitting in.

**Stretch** — publish cost per scan as a metric on the dashboard from
[`P4.4`](../../phase-4/projects/P4.4.md) with an objective attached to it. Only after the ship
checklist is green.
