# P6.5 — `driftwatch-mcp`

> An MCP server on the current spec that lets Claude Code ask your service what's rotting in a repo.

**Phase 6** · ships week 41 · Cloudflare Workers · difficulty High
**Spec:** [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) → search `P6.5`

## Why this one

A coding agent sitting in someone's repo is the right place to ask "what is stale here and what
breaks if I upgrade it?", and the answer already exists behind [`P6.4`](P6.4.md). This makes it
reachable over the Model Context Protocol, so the question gets asked where the work happens
rather than on a web page nobody opens. It lands after [`P6.4`](P6.4.md) for a plain reason:
until retrieval works there is nothing worth exposing, and a tool surface over an empty index
teaches you protocol trivia and nothing else. It is its own repo rather than a `driftwatch`
layer because it is a protocol adapter with its own threat model and release cadence, and
because it is the spine artifact you can hand to a stranger. [`P6.6`](P6.6.md) then builds the
agent that consumes it, and the capstone [`C1`](../../phase-8/projects/C1.md) counts MCP as one
of the eight topics it composes.

## What you'll be able to do after

- You will have implemented a server against the MCP specification itself rather than a tutorial,
  and can say which parts of the protocol you used and which you deliberately did not.
- You will have written tool descriptions and can explain that the description *is* the
  interface — a model picks a tool by reading it, so ambiguity is a bug.
- You will have written a threat model treating each tool as a security boundary, with
  deny-by-default egress, and can explain why an agent-facing tool is not the same as an API
  endpoint with the same body.
- You will have designed for stateless request/response and can explain what that costs you and
  why it is the right shape on a serverless runtime.

## Where you'll get stuck

- **The SDK is behind the specification.** The spec flags this: the TypeScript SDK may not track
  the revision you are building to, so a feature the spec describes has no method on the client
  → check [`../verified/`](../verified/) for the current SDK state before you start, implement
  against the wire format where the SDK is missing, and keep a list of every gap. That list is a
  strong README section and a legitimate upstream contribution. Do not switch to Python over it:
  the stack constraint holds, and a partial SDK is not a language problem.
- **You implement something the revision deprecated.** Nearly every tutorial demonstrates
  capabilities the current revision is winding down, the client-registration path included →
  read the specification's own deprecation list rather than a blog post, and let the out-of-scope
  list in [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) stop you.
- **The agent calls the wrong tool, or calls it with garbage.** Your instinct will be to fix the
  code; the fix is the description and the schema, because that is all the model sees → make
  each tool narrow, name arguments unambiguously, and test several phrasings of one request.
- **State you assumed you had.** A serverless runtime gives you no in-memory session between
  calls, so anything cached mid-conversation vanishes → every tool must be answerable from its
  arguments plus the database, which is what stateless means in practice.
- **Auth works locally and fails from a real client.** Callback and metadata origins are
  registered once and differ between local and deployed → this is where the 2-hour rule from
  [`plan/01-roadmap.md`](../../../plan/01-roadmap.md) fires: falsifiable sentence, smallest
  reproduction, then the specification's own auth section.

## The interview angle

This is the most current thing in the plan, and built against the specification rather than a
tutorial it is also the rarest. It lets you answer "how do you safely expose a system to an
agent?", which is a security question rather than a plumbing one. The system-design rep buried
in it is tools as trust boundaries: authorization per tool, egress control, and blast radius
when the caller is a model that can be talked into things. Resume line: *an MCP server exposing
a dependency-currency service to coding agents, with per-tool threat modelling and
deny-by-default egress.* The follow-up a good interviewer asks is what stops an agent chaining
your tools into an effect you did not intend; the honest answer is the boundary per tool, that
red-teaming the surface was the stretch goal, and that nothing here writes — writes start at
[`P6.6`](P6.6.md), behind a human.

## Scope discipline

**Out of scope** — do not implement the capabilities the current revision deprecates (the spec
names them, and the wind-down window is not permission), no stdio transport, no multi-agent
orchestration. Building deprecated features is the single easiest way to lose a week here and
end up with a server that reads as dated.

**Stretch** — a red-team suite against the MCP surface, mapped to the OWASP MCP top-ten list.
Only after the ship checklist is green.
